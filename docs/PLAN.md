This document is the **authoritative technical and product plan** for the
Complex Trading Journal project.

It describes:
- product behavior
- backend + frontend architecture
- database model
- alert → position linking logic
- chart generation strategy
- IBKR integration boundaries

Codex missions must **follow this plan** and the rules in `AGENTS.md`.

---

## 1. Product Goal

Build a **personal trading journal command center** that connects:

1. Alert trigger events (from Supabase, generated by an existing Python alerts engine)
2. Interactive Brokers account data (READ-ONLY)

The system is designed to analyze **behavior and decision quality**, not to trade automatically.

Core idea:
> Connect **signal → decision → position → outcome**

---

## 2. Core Product Principles (Non-Negotiable)

- This is a **journal**, not a live trading terminal
- History and snapshots matter more than real-time data
- IBKR access is **read-only** (no orders, no automation)
- Alerts are frequent; the UI must be calm and decision-oriented
- Charts are **static, deterministic images** generated by backend
- Frontend never talks directly to Supabase or IBKR
- UTC is used everywhere in backend & database

## 4. Alerts Source (Supabase)

### Table: `alerts_triggers`

Each row represents **one trigger event**.

Columns used by this project:

- `id` (UUID) — trigger event ID (**primary key for journal logic**)
- `alert_id` (UUID) — alert definition (grouping only)
- `symbol` (TEXT) — ticker
- `alert_type` (TEXT) — e.g. `sma_touch`
- `condition` (JSON text) — parameters (sma_period, tolerance_pct, etc.)
- `triggered_at` (TIMESTAMPTZ, UTC)
- `price` (NUMERIC)
- `message` (TEXT)
- `snapshot` (JSON text) — SMA values, ATR, price context, etc.

Important:
- The **feed uses `alerts_triggers.id`**, not `alert_id`
- One alert definition can produce many trigger events

## 5. Alert Feed Behavior

### Definition
The Alerts page is a **decision queue**.

### Inclusion rule
An alert trigger appears in the feed if:
- It has **zero rows** in `trigger_position_links`

An alert disappears from the feed only when:
- It is linked to at least one position

Viewing an alert does **not** remove it.

This allows:
- Alert fires
- Position opened days later
- Alert still linkable
- Once linked → removed from feed

### Update behavior
- No streaming / WebSockets
- Frontend polls backend every ~7 seconds while page is active

## 6. Chart Generation (Static Images)

### Philosophy
Charts must represent **what you saw at the time**, not a mutable live view.

### Chart identity
- One chart per trigger event
- Key = `alerts_triggers.id` (trigger_id)

### File naming
data/charts/triggers/{SYMBOL}/{trigger_id}_v1.png


Example:
data/charts/triggers/CVCO/0a711bfa-f9bc-444e-b497-2a99e23f5557_v1.png


### Versioning
- v1 is default
- Never overwrite existing images
- New algorithms → generate `_v2.png`

### Serving
- Backend serves `./data` at `/static`
- Frontend receives `chart_url` and renders `<img>`

### Retention (MVP)
- Keep all charts
- Later: optional cleanup of **unlinked** triggers after N days
- Linked triggers are retained forever

## 7. New Database Tables (Supabase)

These tables are added by the website layer.

### 7.1 `position_journal`
Represents a position entity used for tagging and linking.

Fields:
- `id` UUID PK
- `ticker` TEXT
- `status` TEXT (`open` | `closed`)
- `open_time_utc` TIMESTAMPTZ NULL
- `close_time_utc` TIMESTAMPTZ NULL
- `origin` TEXT (`manual` | `alert_based`)
- `notes` TEXT NULL
- `created_at` TIMESTAMPTZ

---

### 7.2 `positions_snapshot`
Snapshots of IBKR positions for history.

Fields:
- `id` UUID PK
- `snapshot_time_utc` TIMESTAMPTZ
- `ticker` TEXT
- `quantity` NUMERIC
- `avg_cost` NUMERIC
- `market_price` NUMERIC NULL
- `unrealized_pnl` NUMERIC NULL
- `currency` TEXT NULL
- `raw` JSONB

---

### 7.3 `trigger_position_links`  (Core glue)
Links alert triggers to positions.

Fields:
- `id` UUID PK
- `trigger_id` UUID FK → `alerts_triggers.id`
- `position_id` UUID FK → `position_journal.id`
- `link_type` TEXT:
  - `trigger`
  - `context`
  - `post_entry`
- `created_at` TIMESTAMPTZ
- `created_by` TEXT (optional)

Rule:
- Presence of a row removes trigger from feed

---

### 7.4 `position_tags`
Tags attached to positions.

Fields:
- `id` UUID PK
- `position_id` UUID FK
- `tag` TEXT
- `source` TEXT (`manual` | `auto`)
- `created_at` TIMESTAMPTZ

## 9. Backend API Contracts

### Alerts
- `GET  /api/alerts/feed`
  - returns unlinked triggers + chart_url
- `POST /api/triggers/{trigger_id}/link`

### Positions
- `GET   /api/positions/open`
- `PATCH /api/positions/{position_id}`
- `POST  /api/positions/{position_id}/tags`
- `DELETE /api/positions/{position_id}/tags/{tag_id}`

### Health
- `GET /api/health`

## 10. IBKR Integration

### API
- Client Portal Web API (CP Web API)
- Requires local Client Portal Gateway

### Boundaries
- READ-ONLY
- No order placement
- No cancellations
- No account mutations

### Data used (MVP)
- Open positions
- (Later) historical PnL / executions

Snapshots are stored in `positions_snapshot`.

---

## 11. Frontend Architecture (Next.js + MUI Core)

### UI philosophy
- Light mode
- Calm spacing
- Cards + drawers
- No chart interactivity (static images only)

### Pages

#### `/alerts`
- Search bar
- Filter by symbol / alert_type
- Feed of alert cards
- Inline chart image visible immediately
- Polling every ~7 seconds
- Link action opens right-side drawer

#### `/positions`
- Table of open positions
- Origin badge (manual / alert_based)
- Tags as chips
- Row click opens drawer:
  - edit origin
  - manage tags
  - view linked triggers
  - notes
